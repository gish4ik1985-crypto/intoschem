### 1.2 Генератор платы `web/js/engine/rig.js`

Ключевая вещь всей работы. В фиксированном уровне провода декоративны:
топологию задаёт `build()`, картинку — руками набранные координаты. Эти две
вещи расходятся молча. `Rig` строит **и разводку, и компоненты решателя из
одного описания рядов**, поэтому разойтись им негде.

```js
const L = Rig.rows({
  id: 'имя',
  board: DB.m.board,
  busX: { REF: 0.35 },          // доля ширины для колонки именованного узла
  supply: { id:'SUP', name:'…', label:'12 В', silk:'G1', value:12, rInt: … },
  rows: [
    { id:'TOP', to:'REF', rated:0.3, items:[ …детали… ] },
    { id:'BOT', from:'REF',          items:[ …детали… ] },
  ],
});
// дальше в уровне:
parts: L.parts, wires: L.wires,
build: (c, P) => Rig.build(c, P),
apply: (refs, P, c) => Rig.apply(c, refs, P),
```

Форма платы одна на все уровни: слева блок питания, от него вертикальная шина
VCC, справа вертикальная шина GND, между ними горизонтальные ряды. Именованный
узел — ещё одна вертикальная колонка между ними; к ней приходят одни ряды и от
неё уходят другие. Так на плате выглядит любой делитель и любая развилка.

Что важно помнить:

- имя промежуточной сети внутри ряда — `<id ряда>_<номер детали>`
  (ряд `BAL`, вторая деталь → сеть `BAL_1`). Через него `read()` берёт
  напряжения;
- `Rig.apply` меняет номиналы только через `setResistance`/`setSwitch` —
  прямое присваивание молча убивает расчёт (см. `CLAUDE.md`);
- `topologyKey` уровням на `Rig` не нужен: смена номинала и положения ключа
  идёт через методы цепи;
- ряды центрируются по вертикали (свободное место делится поровну), детали в
  ряду — по горизонтали между своими колонками;
- обратный провод идёт выше шелкографии платы, знак земли сидит прямо на нём;
- предупреждения («не помещается по высоте», «ряд шире просвета») печатаются
  в консоль при загрузке и видны в прогоне тестов.

### 1.3 Слой тайны (`web/js/scenes/journal.js` + правки HUD/карты/меню)

**Правило, на котором всё держится: тайна живёт в НАЗВАНИИ, а не в задаче.**
Что делать на уровне — по-прежнему открытым текстом в «Задаче», приборах,
статусе и подсказках. Скрыто ровно одно: что это за узел и зачем он в изделии.
Ни одна механика не спрятана, ни одно число не убрано — обучающая часть цела.

Как устроено:

- `SECTORS` в `journal.js` — пять секторов (A ПЕРИФЕРИЯ, Б СИЛОВАЯ ЧАСТЬ,
  В ИЗМЕРЕНИЕ, Г УПРАВЛЕНИЕ, Д ЯДРО) со списком id уровней **в порядке
  прохождения**. Из позиции в этом списке считается обозначение узла
  («Б-12»), которое видно вместо названия;
- `LevelRegistry.register` (в `level.js`) сам проставляет `spec.sector` и
  `spec.codename` — уровню это писать не надо;
- HUD показывает «УЗЕЛ Б-12» и «НАЗНАЧЕНИЕ НЕ ОПРЕДЕЛЕНО» вместо названия,
  пока узел не восстановлен; на карте и в подсказке — то же самое;
- у каждого уровня есть `reveal` — одна строка журнала, которая открывается
  при первом восстановлении. Для семнадцати старых уровней строки лежат
  таблицей `LEGACY_REVEAL` в том же файле (не правкой семнадцати файлов);
- журнал открывается кнопкой из главного меню, из паузы и из шапки уровня;
  сектор, собранный целиком, отдаёт свою итоговую строку;
- нового сохраняемого состояния не заведено: журнал считается из
  `GameConfig.isRepaired`.

Сюжет: изделие — автономный зонд; ремонтная подсистема (игрок) осталась одна,
операторы не вернулись. Сектор Д отвечает, что это за изделие.

Приёмы, которые пригодятся в оставшихся уровнях:

- **импульсная нагрузка** (`b_reference`): ключ без `interact`, которым щёлкает
  сам уровень из `tick`. Нужен там, где постоянную нагрузку можно «подогнать»
  и урок не состоится;
- **пик тока** (`b_inrush`): каркас пишет `part.iMax` внутри шагов решателя;
  уровень обязан обнулять его, когда пуск не идёт, иначе неудачная первая
  попытка навсегда останется в памяти и уровень станет непроходимым;
- **сгорание как отсев** (`b_derate`): неправильный, но проходящий по току
  ответ выгорает раньше, чем истекает `hold`. Время до сгорания считается как
  `tau * ln(1/(1 - pMax/p))` и обязано быть заметно меньше `hold`.

### Раскладка на карте

Секторы идут цепочкой от `workbench`, расстояние между соседями 260–320 при
радиусе света 900 — проверяется автоматически (`levels.test.js`, группа
«Карта: свет дотягивается до соседа»).

**Компактность.** Первая версия раскладки (шаг ~260–300, как у старых 17
уровней) уводила весь новый блок на несколько тысяч пикселей левее старого
кластера — игрок жаловался «уровни куда-то поскакали далеко», приходилось
долго скроллить. Позиции всех 30 узлов пересчитаны как компрессия к якорю
`workbench` (-1420, 1260): `новая = якорь + (старая - якорь) × 0.8`. Меньший
множитель (пробовал 0.55) сближает узлы слишком сильно — карточки на карте
168×114, и при 0.55 тридцать восемь пар начинали перекрываться; 0.8 —
минимум, при котором пересечений нет (проверено скриптом, сравнивающим
прямоугольники карточек с отступом). Проверять после любого сдвига позиций
именно так, а не только тестом на «до соседа хватает света» — тот не видит
геометрических наездов карточек друг на друга, только оптическую дальность.


### Порядок действий на каждый новый уровень (если будут ещё)

1. Написать файл `lNN_<id>.js` по образцу готовых.
2. Добавить id в нужный сектор в `journal.js` (порядок = порядок прохождения,
   из него считается обозначение узла).
3. Перегенерировать список `<script>` уровней в `index.html`
   (в файлах уже отсортированный порядок `l\d\d`).
4. `node web/tests/run.js` — должно быть 0 новых замечаний.
5. Прогнать перебор победных состояний (скрипт `win.js`, см. ниже) и
   убедиться, что выигрывает задуманный ответ, а не что-то вырожденное.

Перебор победных состояний — отдельный скрипт, он не входит в набор тестов
(долгий). Смысл: `levels.test.js` отвечает «победа достижима», а перебор
отвечает «и достижима она ровно тем, что задумано». Второй вопрос важнее
первого: уровень, у которого шесть проходных ответов вместо одного, формально
исправен, а урока не даёт — так было с `b_reference` до переделки нагрузки на
импульсную.

# Ветка работ 3 (2026-09-02, вечер): карта-граф и узлы без питания

Три просьбы игрока: собрать уровни в одном месте, дать возможность приходить к
узлу с нескольких сторон, и сделать уровни, где своего питания нет и его надо
тянуть от соседей.

## Что сделано

### Карта стала графом и переехала в одно место

- `map.from` принимает список родителей; `isLit()` открывает узел от ЛЮБОГО из
  них, кабели рисуются от всех, проверка света требует, чтобы дотягивался
  каждый;
- новый генератор `web/tests/_maplayout.js` раскладывает секторы блоками и
  считает связи по близости. Поле сжалось с ~4700×3400 до 1935×2595, связей
  145, узлов с двумя подводящими линиями — 66;
- раскладка и связи записываются прямо в файлы (`--write`), правка ограничена
  блоком `map: { ... }`.

### Три узла без собственного питания (сектор Ж · ПЕРЕМЫЧКИ)

`Rig.rows` научился ставить вместо блока питания **клеммники ввода**
(`cfg.feeds`), новая деталь `Parts.feed`.

| id | Урок | Ответ |
| --- | --- | --- |
| u_share | две линии делят ток обратно пропорционально сопротивлению | догрузка 10 Ом в короткую линию |
| u_bridge | диодная развязка основного и резервного вводов | диод в резервный ввод |
| u_transit | общий провод несёт СУММУ своего и транзитного тока | жила 2,5 мм² |

`u_bridge` роняет основной ввод сам раз в две секунды — иначе резерв никогда бы
не вступил и проверить его было бы нечем. `u_transit` отсеивает средний вариант
сгоранием: по напряжению он проходит, по нагреву — нет.
